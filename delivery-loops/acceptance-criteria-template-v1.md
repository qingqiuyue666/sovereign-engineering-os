## Purpose

Define what the buyer/operator must accept before a bounded delivery can be
called complete.

## Acceptance Record

```text
date:

review owner:

accepted behavior:

known limitations:
incomplete items:
failure cases reviewed:
rollback reviewed:
maintenance decision:
accepted / accepted with limitations / rejected / incomplete:
reviewer:
```

## Required Acceptance Criteria

The delivery is complete only if the reviewer confirms:

- the workflow is the one accepted in scope
- the SOP/checklist is understandable
- human review points are clear
- forbidden automatic actions are excluded
- output can be inspected
- failure handling is documented
- rollback is understood
- limitations are recorded
- evidence package is available

## Not Accepted If

Do not mark complete if:

- reviewer did not inspect output
- evidence is missing
- the workflow changed without approval
- secret handling occurred
- external actions occurred without review
- rollback is unclear
- the buyer asks for unsupported ROI, certification, or guarantee claims

## Claim Boundary

Acceptance of one delivery is not:

- repeated delivery
- product-market fit
- SaaS readiness
- ROI proof
- certification
- external audit
- protocol adoption
- capital readiness
