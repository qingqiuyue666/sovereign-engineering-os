## 4. Design Problem

The design problem is whether any future Python-based skeleton shape can remain genuinely non-runtime without creating importable ambiguity, package ambiguity, executable ambiguity, validation ambiguity, or authority ambiguity.

A `.py` file is not merely documentation. Even if empty or docstring-only, it can become an importable module and therefore creates a different risk-category than Markdown marker files.

## 5. Unsafe Shape Evaluation

| Shape | Decision | Reason |
| --- | --- | --- |
| package-based skeleton using __init__.py | Rejected for current phase. | Creates package discovery ambiguity and can suggest sanctioned module boundaries. |
| import-bearing skeleton | Rejected for current phase. | Creates dependency-loading ambiguity and can imply executable readiness. |
| class-based skeleton | Rejected for current phase. | Creates object-shape ambiguity and can imply authorized adapter construction. |
| dataclass-based skeleton | Rejected for current phase. | Creates data-contract ambiguity and can imply schema-ready runtime participation. |
| protocol-based skeleton | Rejected for current phase. | Creates interface ambiguity and can imply implementation compatibility. |
| schema-based skeleton | Rejected for current phase. | Creates validation ambiguity and can imply accepted runtime data shape. |
| validator-based skeleton | Rejected for current phase. | Creates enforcement ambiguity and can imply authority over admissibility. |
| runtime-function skeleton | Rejected for current phase. | Creates callable execution ambiguity and can imply runtime entrypoints. |
| raising-function skeleton | Rejected for current phase. | Creates callable-surface ambiguity even when behavior only rejects. |
| empty .py skeleton | Rejected for current phase. | Creates importable-module ambiguity despite lacking body content. |
| docstring-only .py skeleton | Rejected for current phase. | Creates importable-module ambiguity while presenting as documentation. |
| importable runtime-surface stub | Rejected for current phase. | Creates runtime-surface ambiguity and can be mistaken for usable authority. |
| CLI skeleton | Rejected for current phase. | Creates operator-command ambiguity and can imply execution capability. |
| service/repository/executor skeleton | Rejected for current phase. | Creates integration-path ambiguity with service, persistence, and execution surfaces. |
| subprocess/network/tool-control skeleton | Rejected for current phase. | Creates external execution and physical-I/O ambiguity. |
| files under kernel/adapters/ | Rejected for current phase. | Creates proximity ambiguity with the existing adapter lane. |
| files that appear to extend the existing Anthropic adapter lane | Rejected for current phase. | Creates continuity ambiguity with the pre-existing phase-1 real-model ignition lane. |

## 10. Future Gate

A future Python skeleton implementation decision audit is blocked unless it can prove concrete necessity.

Concrete necessity requires exact evidence that one of these is true:

- a specific existing SEOS narrow-kernel behavior cannot be validated or used without Python skeleton code
- a specific lifecycle/replay/demo/dry-run manifest boundary is untruthful without Python skeleton code
- a specific current-phase/public-overview/release/contract/design/marker claim requires Python skeleton code to remain truthful
- a specific acceptance surface cannot remain valid without Python skeleton code

Convenience, ambition, desire to move faster, generic skeleton usefulness, generic adapter usefulness, and desire to control tools are not concrete necessity.

## 11. Next Step

The next step should not be Python skeleton implementation by default.

The next step should be a skeleton-code-design-consolidation-audit-v1.

That audit should decide whether the code-design line is complete and whether to stop, consolidate, or open a later implementation decision audit.
