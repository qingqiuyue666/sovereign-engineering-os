# First Wedge Selection

## Purpose

Select the first bounded market wedge for immediate execution while keeping
the decision below the evidence currently available.

## Scope

Applies to the next 90-day market test after this assembly pass.

## Non-goals

- This is not a claim of paid traction.
- This is not a final company strategy.
- This does not reject other wedges permanently.

## Decision

Provisional first wedge: **AI Engineering Production Governance**.

Decision status: **recommended, pending real paid signal**.

## Rationale

This wedge best matches existing repository assets: approval gates, evidence
traces, audit reports, WAL/replay concepts, failure bundles, controlled
execution boundaries, policy checks, and no-fake-success rules. It also has
a direct trust gap: AI-written code entering production creates review,
rollback, acceptance, ownership, and audit pressure that generic code
generation does not solve.

## Buyer Hypothesis

- Buyer: engineering leaders, founders, platform owners, and AI-adoption
  owners in small to mid-sized teams shipping AI-assisted code.
- Budget source: engineering productivity, security/compliance, release
  quality, incident prevention, developer tooling, audit readiness.
- Buying trigger: AI code use is increasing and leadership needs production
  gates before incidents, audits, customer review, or release deadlines.
- Trust gap: teams cannot trust AI code unless evidence, tests, rollback,
  provenance, and review boundaries are visible.

## Entry Offer

"AI Production Governance Readiness Audit": a 5-10 day bounded review that
maps AI-written code admission, review gates, tests, rollback, evidence,
ownership, and release risk. Output is a scored governance report, one
prioritized remediation plan, and one reusable task-package standard.

## Acceptance Criteria

- Buyer can name current AI-code production path and risk owner.
- Deliverable includes evidence matrix, risk tiers, review gates, rollback
  plan, and task package template.
- No production authority is assumed by SEIS.
- Any claims of readiness are tied to provided evidence.

## Operating Rules

- Run discovery before build work.
- Reject prospects seeking uncontrolled automation or secret handling.
- Convert every delivery into proof assets and registry entries.
- Do not claim standards or certification until repeated buyers accept the
  same package.

## Failure Modes

- The buyer wants cheap code review rather than governance.
- The team lacks authority to change production workflow.
- The offer drifts into generic AI consulting.
- Delivery cannot access enough evidence to produce a truthful report.

## Upgrade Path

If paid signal exists, promote into a standardized delivery system with
case study, acceptance standard, review-gate template, pricing history, and
proof package.
