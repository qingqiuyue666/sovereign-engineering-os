## Implementation Constitution and Roadmap
### Kernel + Project OS + Multi-Vendor Capability Strategy
**Version:** Integrated Architecture Baseline v11

## 0. Executive Definition

This system is not a chat assistant.  
It is not a prompt wrapper.  
It is not an IDE plugin bundle.  
It is not a terminal toy.  
It is not “one strong model does everything.”  
It is not merely a coding tool.

It is a **Sovereign Engineering Operating System** whose kernel governs truth, legality, approvals, replay claims, recovery, and side-effect authority across the full lifecycle of engineering work.

Its constitutional rules are:

1. The system owns truth.
2. The system owns state transitions.
3. The system owns approvals, permissions, and side-effect authority.
4. The system owns replay claims, audit evidence, and recovery guarantees.
5. Models are bounded cognitive workers, not sources of truth.
6. Cloud vendors, plugins, tools, runners, and model APIs are subordinate execution resources, never hidden authority channels.
7. The system is local-first in authority, evidence, and recoverability, even when later phases admit remote execution surfaces.
8. Coding is one lane of the system, not the identity of the system.

**One-line rule**

Models may think, search, explain, compare, plan, and generate.  
Only the system may define truth, mutate state, approve effects, seal revisions, record evidence, classify replay fidelity, and claim recoverability.

**Practical translation**

- Intelligence is replaceable.
- Authority is not.
- Workers are replaceable.
- Truth is not.
- Coding is one lane.
- Governance is permanent.
- Evidence is mandatory.
- Replay claims are bounded by captured reality, not desire.

This system is not defined as “an AI that writes code.”  
It is defined as a sovereign engineering operating system that plans, designs, implements, validates, reviews, governs, audits, replays, recovers, releases, and evolves software projects end-to-end.

This document is the governing implementation constitution and execution roadmap for the system.

## 1. Primary Mission

Primary mission:

Build a local-first, state-sovereign engineering operating system that can survive real software engineering conditions and govern the full lifecycle of work:

- requirement interpretation
- project planning
- architecture design
- implementation
- validation
- review
- approval
- side-effect control
- release gating
- audit
- replay
- recovery
- long-term evolution

This system is not optimized for demo throughput.  
It is optimized for control, correctness, survivability, and project-scale execution.

Success does not mean “the model sounds smart.”  
Success means:

- repository truth is system-owned
- revisions are legal and recoverable
- model proposals cannot bypass validation or approval
- side effects are capability-gated and policy-gated
- context construction is deterministic within declared limits
- replay claims are honest
- audit evidence explains why something happened
- crash recovery returns to a known legal sealed state
- retries and budgets cannot run unbounded
- validation catches real mistakes
- large repositories remain operable through incremental invalidation
- project work can be orchestrated across multiple lanes without surrendering kernel sovereignty
- temporary substrates are replaced only when justified by measured failure data
- irreversible effects require stronger evidence, stronger authority, and stronger audit than reversible effects

Secondary mission:

Turn frontier models into interchangeable workers under one authority model.  
The objective is not to worship any vendor.  
The objective is to subordinate multiple strong vendor capabilities to one sovereign kernel.

**Failure definition**

The system is considered failed if any of the following occur:

- truth can be silently mutated outside kernel authority
- approval can time-travel across drift or concurrency races
- replay labels exaggerate what evidence supports
- validation can be bypassed or faked
- side effects can begin without valid capability and policy checks
- crash recovery invents sealed truth that never crossed a legal durability boundary
- audit queries cannot reconstruct why a material action happened
- temporary execution convenience becomes a permanent hidden authority channel
- model outputs are treated as truth-bearing without governed artifact conversion

## 3. Core Design Doctrine

### 3.1 Truth sovereignty

No prompt, model memory, runner output, plugin, tool side effect, or cloud API result may define truth.  
Only the kernel does.

### 3.2 Default deny

No revision seal, external side effect, outbound network action, high-privilege tool use, or sensitive evidence export occurs without explicit capability and policy authorization.

### 3.3 Explicit replay honesty

The system never claims a replay level beyond what captured evidence physically supports.  
A persuasive rerun is not exact replay.  
A semantically similar outcome is not exact replay.  
A cloud re-query is not exact replay.

### 3.4 Evidence first

Important actions must be reconstructable from evidence, not inferred after the fact.  
If the system cannot prove why an action occurred, the system must classify that action as insufficiently evidenced.

### 3.5 Safety and liveness

The system must prevent corruption and runaway behavior while still making bounded progress under admitted load.  
No safety mechanism is acceptable if it silently invents truth.  
No liveness mechanism is acceptable if it silently bypasses authority.

### 3.6 Controlled cognition

Workers are bounded proposal engines, not authorities.  
Workers may propose, compare, search, summarize, and generate.  
They may not self-authorize, self-approve, self-seal, self-classify replay, or self-grant capability.

### 3.7 Enterprise code sovereignty

Telemetry, replay bundles, evaluation corpora, and debug exports must not become covert code exfiltration channels.  
The system must treat proprietary code, manifests, internal topology, and evidence artifacts as controlled material.

### 3.8 Local-first heavy-load awareness

The system must explicitly govern:

- memory pressure
- swap onset
- disk growth
- cache pollution
- hostile APIs
- queue starvation
- long-runner suspension
- workstation collapse

### 3.9 Monotonic causality

Causal order is defined by logical sequence, not wall-clock.  
Wall-clock time is metadata, not authority.  
If causality is ambiguous, the system must fail closed rather than invent a legal ordering.

### 3.10 No new constitutional rules without physical evidence

After this document, new top-level rules are legitimate only if driven by:

- implementation failures
- replay breaks
- benchmark collapses
- governance incidents
- recovery ambiguities
- authority boundary violations

### 3.11 Authority locality

Authority must remain local to the kernel even when workers, tools, runners, or future remote execution surfaces are distributed.  
A distributed worker surface does not imply distributed sovereignty.

### 3.12 Explicit downgrade discipline

When guarantees weaken, the system must downgrade its claim language, artifact class, replay class, or approval admissibility rather than hiding degradation behind polished output.

### 3.13 Minimality at the hot path

The system must aggressively distinguish hot-path authority logic from cold-path analysis logic.  
Authority checks, revision legality checks, approval barrier checks, and capability validation belong to hot-path governance and must not be bloated by project-scale analysis, narrative summaries, or batch intelligence layers.

### 3.14 Replacement-by-evidence doctrine

Temporary substrates, temporary validators, temporary runners, and temporary replay paths are allowed.  
They are not weaknesses if honestly declared.  
They become weaknesses only if preserved without evidence-based review.

## 4. System Shape

The system has two major bands:

**A. Sovereign Kernel**  
**B. Engineering Capability Band**

### 4.1 Sovereign Kernel planes

1. Truth Plane
2. Validation Plane
3. Execution Plane
4. Control Plane
5. Context Plane
6. Evidence Plane
7. Learning Plane
8. Periphery Plane

### 4.2 Engineering Capability Band

1. Planning Lane
2. Architecture Lane
3. Coding Lane
4. Validation Lane
5. Review Lane
6. Async Backlog Lane
7. Repo Intelligence Lane
8. Release / Operations Lane

### 4.3 Shape rule

The kernel owns truth, authority, and admissibility.  
The capability band consumes kernel contracts and produces governed proposals.  
No lane may silently bypass a plane.  
No plane may silently delegate sovereignty upward or outward.

### 4.4 Plane semantics

**Truth Plane** — owns durable truth, revision legality, causality, snapshot identity, and recovery eligibility.  
**Validation Plane** — determines whether a proposed mutation is legally admissible before truth changes.  
**Execution Plane** — performs effects but does not define truth or approve itself.  
**Control Plane** — owns approvals, capabilities, budgets, retries, drift handling, taint posture, scheduling, and route governance.  
**Context Plane** — constructs bounded, deterministic, provenance-rich context for workers and reviewers.  
**Evidence Plane** — proves what happened and what can honestly be claimed.  
**Learning Plane** — learns only on governed evidence and never bypasses provenance.  
**Periphery Plane** — provides user-facing and ecosystem-facing surfaces without seizing sovereignty.

### 4.5 Lane semantics

**Planning Lane** — turns ambiguous goals into executable project structure.  
**Architecture Lane** — makes structural design decisions before implementation emission.  
**Coding Lane** — performs implementation work under governed mutation rules.  
**Validation Lane** — runs legality, coherence, and regression checks.  
**Review Lane** — renders cognitive and risk legibility for approval and audit.  
**Async Backlog Lane** — executes deferred or long-tail work under the same kernel governance model.  
**Repo Intelligence Lane** — maps repository structure, technical debt, and dependency topology.  
**Release / Operations Lane** — governs release readiness, rollback readiness, and environment-sensitive execution consequences.

## 5. Hardware and Deployment Baseline

Primary baseline:

- Apple MacBook Pro with M5 Max
- 64 GB unified memory
- 2 TB internal storage
- optional external SSD expansion
- local-first preferred
- single-user or small-team initial mode

Implications:

- medium-to-large text-first repositories are feasible locally
- strict working-set discipline is mandatory under simultaneous inference + validation
- disk growth must be governed from day one
- macOS-specific isolation strategy must be explicit for validation quarantine
- cross-platform bit-identical replay is not assumed
- remote collaboration requires a later persistence and coordination strategy

### 5.1 Baseline hardware rule

The machine is not an abstraction layer. Its memory ceiling, storage profile, process behavior, filesystem semantics, and local sandbox limitations shape the implementation.

### 5.2 Local-first execution consequences

- the system must tolerate medium and large local repository indexing
- the system must distinguish foreground latency from background indexing and validation load
- the system must explicitly budget memory for simultaneous context construction, validation, and worker execution
- the system must suspend or degrade non-critical lanes under pressure before the workstation collapses

### 5.3 Anti-swap posture

The system must treat swap onset as a governance event, not a purely operating system concern.

### 5.4 Disk governance

The system must govern artifact store growth, replay retention, evidence retention, quarantine churn, worktree duplication, benchmark corpus growth, and failure bundle retention.

### 5.5 Platform-specificity rule

The baseline platform is macOS on Apple Silicon.  
Validation isolation strategy, filesystem assumptions, replay exactness, and toolchain fingerprinting must remain explicit.

## 19. Implementation-Grade Definition

A document or subsystem may be called implementation-grade only if all are true:

- core contracts have formal bodies, not only headings
- frozen schemas exist at field level for core artifacts
- invariant -> enforcement point -> acceptance test bindings are explicit
- replay classes have admission criteria and downgrade rules
- atomic approval barrier has concurrency semantics
- validation quarantine has platform-specific execution rules
- capability security has a defined trust boundary and threat model
- context completeness rules are explicit
- retention and pinning rules are explicit
- failure reactions are specified, not implied
- audit evidence requirements are explicit per critical action

Until those conditions are satisfied, the system remains an implementation constitution and roadmap, not a fully signed implementation-grade contract set.


### 19.1 Capability Security Trust Boundary and Threat Model

Capability security is implementation-grade only if the trust boundary and minimum threat model are explicit, durable, auditable, and enforced at effect time rather than inferred from worker intent.

#### Trusted components

The following components are trusted to participate directly in capability issuance, verification, revocation, and enforcement:

- Sovereign kernel authority path
- Capability authority
- Policy registry and policy evaluation path
- Durable journal / evidence write path used to record issuance, consumption, revocation, and rejection
- Cryptographic verification path used to validate token integrity
- Atomic approval barrier when the capability class requires prior approval
- Drift reconciliation path when drift can invalidate previously legal authority

Trusted does not mean infallible. It means these components are part of the system's authority boundary and must therefore be hardened, audited, and version-bound.

#### Conditionally trusted components

The following components may participate in execution but are not allowed to redefine authority:

- Isolated validation runners
- Worktree runners
- Diagnostic runners
- Replay runners
- Approved local tool wrappers
- Local storage substrates admitted by current policy

These components are conditionally trusted only within the scope explicitly granted to them. They may execute, observe, or transport capability-bearing state, but they may not widen scope, mint new authority, or silently preserve authority across drift.

#### Untrusted or non-authoritative components

The following components are never authoritative even when they are useful:

- Frontier model workers
- Raw prompt outputs
- Plugins before capability verification
- External tool outputs before governed ingestion
- Repository text, retrieved web text, and user-provided free text before artifact conversion
- Any token-shaped value not validated by the kernel
- Remote services that return "permission granted" style responses without local capability validation
- Render layers, dashboards, or UIs that display approval-like state without durable backing artifacts

These components may propose, suggest, or request. They may not authorize.

#### Security principle

Authority must be created only by the capability authority, scoped only by policy, verified only by trusted kernel paths, and consumed only at a legally admissible effect boundary.

No worker, plugin, runner, tool, or remote service may acquire, preserve, widen, replay, or reclassify authority outside this path.

If the system cannot prove that a capability is valid, in-scope, unrevoked, unexpired, admissible for the requested effect class, and still legal under current drift state, the effect must not begin.

#### Minimum threat model

The minimum threat model explicitly includes the following classes of failure or abuse:

1. **Compromised worker output**  
   A worker may emit forged capability-like data, malformed authority requests, or outputs that attempt to bypass approval or policy.

2. **Stolen token**  
   A previously issued token may be copied from logs, memory, temporary files, runner state, or external traces.

3. **Replay of consumed token**  
   A single-use token may be resubmitted after legal consumption in an attempt to execute a second effect.

4. **Cross-worktree or cross-task leakage**  
   A token issued for one task, root, or worktree may be reused in another scope.

5. **Runner compromise or runner overreach**  
   A validation runner, diagnostic runner, or tool wrapper may attempt to persist tokens, exfiltrate secrets, or widen its own execution rights.

6. **Drift-after-issuance abuse**  
   A token that was legal at issuance time may be used after root drift, task supersession, policy drift, or approval invalidation.

7. **Secret-bearing escalation**  
   A token that permits ordinary execution may be abused to reach secret-bearing, network-bearing, or irreversible-effect paths.

8. **Partial crash ambiguity**  
   The system may crash after token validation but before durable consumption, or after partial effect start but before durable recording.

9. **Revocation race**  
   A token may be presented concurrently with a revocation event, drift event, or barrier invalidation event.

10. **Version incompatibility abuse**  
    A token issued under one policy or schema version may be replayed under another in hopes of inheriting stale semantics.

11. **UI or render-layer authority illusion**  
    A user-facing layer may appear to show legal approval or capability state even though no durable authority artifact exists.

12. **Historical evidence misread as live authority**  
    Replay, audit, or forensic artifacts may be mistaken for current executable privilege.

This threat model is minimum, not exhaustive. Any newly discovered exploit path that can widen or preserve authority outside kernel rules must be added to the formal threat model before the system can continue to claim implementation-grade status.

#### Security invariants

The capability system must enforce at least the following invariants:

- **INV-CAP-ONLY-KERNEL-ISSUED**  
  Only the capability authority may issue valid capability tokens.

- **INV-CAP-VERIFY-BEFORE-EFFECT**  
  Capability structure, signature or MAC, scope, expiry, revocation state, and bound identifiers must all be verified before any effect begins.

- **INV-CAP-NO-SCOPE-WIDENING**  
  Scope may not be widened by worker output, runner context, or UI state.

- **INV-CAP-SINGLE-USE-MEANS-SINGLE-USE**  
  Consumed single-use tokens can never be legally accepted again.

- **INV-CAP-NO-DRIFT-CARRYOVER**  
  Root-bound, task-bound, and policy-bound authority may not survive unauthorized drift.

- **INV-CAP-REVOCATION-WINS**  
  A revoked token is invalid even if every other validation property would otherwise pass.

- **INV-CAP-HISTORY-IS-NOT-LIVE-AUTHORITY**  
  Historical capability evidence may support audit or replay classification, but it may not silently reconstitute live execution privilege.

- **INV-CAP-NO-CROSS-CLASS-ESCALATION**  
  Ordinary execution privilege may not be treated as secret-bearing, network-bearing, approval-bearing, or irreversible-effect privilege without fresh issuance under the correct class.

- **INV-CAP-CRASH-AMBIGUITY-FAILS-CLOSED**  
  If crash state leaves authority consumption or effect start ambiguous, the system must resolve in favor of denying further authority until legal state is re-established.

- **INV-CAP-UI-STATE-IS-NOT-AUTHORITY**  
  Rendered approval or status indicators are informational only unless backed by durable authority artifacts.

#### Failure posture

The failure posture is fail-closed.

If the system cannot prove all of the following at effect time:

- capability integrity
- issuer legitimacy
- scope legality
- expiry admissibility
- non-revocation
- non-consumption where applicable
- task/root binding admissibility
- compatibility with current policy and drift state
- correct effect-class authorization

then the requested effect must not begin.

Failure handling must include, where applicable:

- capability rejection
- token revocation or quarantine
- audit record emission
- taint escalation on suspicious abuse
- barrier invalidation when approval-backing conditions no longer hold
- replay downgrade if capability history can no longer justify prior replay claims
- incident escalation if authority ambiguity cannot be resolved automatically

The system may never trade authority certainty for convenience, worker momentum, or UI smoothness.

## 22. Core Contract Bodies

### 22.1 WAL Durability and Recovery Contract

**Purpose**  
Define the minimum durable truth spine for revisions, journal entries, and recovery.

**Scope**  
Applies to all truth-bearing mutations, seal operations, journal persistence, and crash recovery behavior.

**Preconditions**

- a valid originating intent exists
- the mutation has passed required validation gates
- the target root revision is current and legal
- the system is not in a recovery-blocked or corruption-blocked state

**Required fields**

- wal_frame_id
- logical_sequence
- frame_type
- kernel_schema_version
- journal_schema_version
- revision_id
- parent_revision_id
- snapshot_root_id
- payload_hash
- payload_length
- checksum
- committed_flag
- timestamp_metadata
- causality_ref

**Legal rules**

- every truth-bearing mutation must be representable in WAL
- logical_sequence must be strictly monotonic
- fsync discipline must be declared by operation type
- seal may not be acknowledged before the durability boundary
- partial writes must be detectable by checksum and frame completeness rules
- dirty-tail corruption may be truncated only when all preceding frames form a legal sealed history
- mid-segment corruption must halt automatic recovery

**Failure reactions**

- truncate tail and recover
- halt recovery and require operator intervention
- downgrade replay claims if evidence continuity breaks
- invalidate approvals touching corrupted regions
- emit FailureBundle and AuditRecord

**Acceptance criteria**

- crash before seal never produces a sealed revision
- dirty-tail damage truncates safely
- mid-segment corruption halts recovery
- logical-sequence discontinuity is detected
- recovery returns the last legal sealed state, not the last partially written state

### 22.2 Seal Transaction Ordering Contract

**Purpose**  
Define the exact ordering, atomicity, and crash semantics of revision sealing.

**Scope**  
Applies to every transition from pending revision to sealed revision.

**Preconditions**

- originating intent is executable
- current root matches the validated root
- required validation receipts are valid
- approval, if required, is valid and not expired
- barrier checks have passed

**Required checks**

- snapshot candidate exists
- journal prepare entry exists
- WAL mutation/seal frames exist
- durability boundary is crossed before visibility

**Ordering rules**

1. prepare seal metadata
2. write pending mutation payload
3. persist snapshot root candidate
4. append journal prepare entry
5. append WAL mutation and seal frames
6. cross durability boundary
7. transition revision state from pending to sealed
8. append final seal confirmation entry
9. expose sealed revision as current truth

**Failure reactions**

- reject seal
- roll back pending transition
- mark revision abandoned
- emit FailureBundle
- require manual intervention if ambiguity cannot be resolved from durable evidence

**Acceptance criteria**

- no revision becomes visible as sealed before durability
- recovery never produces duplicate seals
- crash in each ordering window yields deterministic classification

### 22.3 Atomic Approval Barrier Contract

**Purpose**  
Prevent approval time-travel across root drift, receipt drift, context drift, policy drift, and concurrent execution races.

**Scope**  
Applies whenever a reviewed change is converted into executable authority.

**Preconditions**

- ApprovalArtifact exists
- ApprovalArtifact references a known root revision
- associated ContextArtifact exists
- required validation receipts exist
- the task has not been superseded or invalidated

**Required checks**

- current_root == originating_root
- context_artifact still valid
- semantic/build receipts still valid
- no out-of-band drift invalidates reviewed state
- no policy drift invalidates approval legality
- no conflicting seal has superseded the task generation

**Legal rules**

- barrier entry must acquire a revision fence or equivalent serialization guard
- no seal on the same affected root/task generation may commit between successful barrier verification and execution start
- competing approvals on the same task generation must resolve deterministically
- if serialization cannot be established, barrier evaluation must fail closed

**Failure reactions**

- invalidate approval
- invalidate receipts
- force re-review
- emit DriftEventRecord
- emit FailureBundle on barrier crash ambiguity

**Acceptance criteria**

- approval cannot execute across root drift
- approval cannot execute across receipt drift
- concurrent conflicting approval cannot silently pass
- crash at barrier never produces ambiguous “maybe executed” truth without evidence

### 22.4 Validation Quarantine Enforcement Contract

**Purpose**  
Prevent build logic, generators, hooks, or untrusted validation-time execution from contaminating host truth, caches, secrets, or network state.

**Scope**  
Applies to all validation-time execution that is not purely static.

**Preconditions**

- validation action is classified as requiring quarantine
- required capability exists
- quarantine policy allows the runner type
- target repository slice is known

**Required checks**

- network-off
- host read-only exposure
- isolated caches
- disposable filesystem layer
- bounded resources
- secret isolation
- explicit audit entry on enter and exit

**Legal rules**

- per-run disposable workspace must be created
- cache namespace must be isolated
- environment variables must be scrubbed against an allowlist
- secrets must be absent unless explicitly admitted by secret-bearing capability
- teardown must remove disposable workspace and isolated caches unless preserved for forensics

**Failure reactions**

- abort validation
- mark ValidationReceipt invalid
- mark worker or runner tainted if contamination cannot be ruled out
- emit FailureBundle for host pollution risk
- invalidate downstream review if quarantine guarantee was violated

**Acceptance criteria**

- untrusted build logic cannot modify host dependency cache
- network-disabled runs cannot reach outbound endpoints
- disposable workspace is removed or pinned according to policy
- secret-scrubbed runs expose no ambient credentials

### 22.5 Replay Fidelity Contract

**Purpose**  
Define honest replay classes, admissibility rules, downgrade rules, and divergence reporting.

**Scope**  
Applies to any replay claim emitted by the system.

**Preconditions**

- replay request identifies a root revision or replay anchor
- required evidence closure is discoverable
- requested replay class is known to policy

**Required checks**

- truth evidence completeness
- context completeness
- inference artifact availability
- environment capture level
- nondeterminism tolerance class
- divergence reporting path

**Legal rules**

Replay classes:
- exact replay
- diagnostic replay
- semantic replay
- degraded replay
- unreplayable

Exact replay requires all of the following:
- durable truth state fully captured
- environment class captured to required precision
- historical inference artifacts present, or an approved exact-execution proof bundle demonstrating operational equivalence under the same deterministic input surface, the same admissible environment fingerprint class, the same policy version class, and the same replay-class adjudication standard
- no unresolved nondeterminism beyond allowed tolerance

The phrase “equivalence” may not mean similarity, plausibility, or semantically acceptable rerun.  
Equivalence is admissible only when the proof bundle is attached, auditable, and explicitly accepted by replay policy.

Cloud re-query is never exact replay.  
Incomplete environment capture is never exact replay.  
Missing historical inference artifacts forces downgrade unless the proof bundle described above is present and admissible.

**Failure reactions**

- downgrade replay class
- refuse replay
- emit replay divergence record
- emit audit note explaining downgrade reason

**Acceptance criteria**

- cloud re-query without historical inference artifacts cannot be labeled exact replay
- missing evidence forces downgrade or refusal
- replay classification is auditable after the fact
- equivalence substitution without proof bundle is rejected

### 22.6 Capability Token Lifecycle Contract

**Purpose**  
Define how capabilities are issued, scoped, validated, consumed, revoked, audited, and prevented from becoming a replay or privilege-escalation channel.

**Scope**  
Applies to every capability-bearing action, including repository reads, snapshot reads, patch proposal, diagnostics, worktree spawning, generator execution, secret use, network access, and external side effects.

**Preconditions**

- subject_identity is known
- issuing authority is trusted under active policy
- requested capability is declared in the capability registry
- requested scope is representable as a bounded scope_hash
- requested action is not forbidden by policy

**Required fields**

- capability_token_id
- subject_identity
- capability_name
- scope_hash
- issued_at
- expires_at
- issuer_identity
- token_mac_or_signature
- version_tuple_hash
- single_use_flag

**Validation rules**

Before effect execution, the kernel must verify:

- token structure is schema-valid
- MAC or signature verifies successfully
- token is within issued_at / expires_at bounds
- token is not revoked
- token is not already consumed if single_use_flag is true
- capability_name is authorized for the requested action class
- scope_hash covers the requested target and no more than allowed
- bound_task_id, if present, matches current task
- bound_root_revision_id, if present, matches current root
- version_tuple_hash is admissible under active policy

**Failure reactions**

- reject capability use
- revoke token
- mark token invalid
- fail closed on verification error
- emit FailureBundle on ambiguous consumption race
- taint worker or runner if privilege abuse is suspected

**Acceptance criteria**

- unsigned or invalidly signed token is rejected
- expired token is rejected
- revoked token is rejected
- single-use token cannot be consumed twice
- concurrent double-consume resolves deterministically with exactly one winner
- root-bound tokens cannot execute across root drift
- replay cannot silently reuse historical consumed authority

### 24.3 Execution Layering Rule

The system distinguishes between:

- the **Final Target Architecture**
- the **Current Execution Doctrine**

These are not competing systems.
They are two lawful readings of the same governing document at different stages of implementation maturity.

The Final Target Architecture defines the full constitutional surface the system may eventually grow into while preserving sovereignty, governance, replay honesty, auditability, recoverability, and policy control.

The Current Execution Doctrine defines the narrower execution discipline that is lawful, signable, and honest under the current maturity stage and current hardware baseline.

Therefore the current-stage sign-off surface is intentionally narrower than the full constitutional surface.

Current-stage sign-off must concentrate first on one governed path:

Context -> Inference -> PatchProposal -> Validation -> Review -> Approval -> Revision Seal -> Evidence

This rule means:

- the kernel core remains the load-bearing sign-off center
- broader orchestration shell behavior remains constitutionally valid but is not automatically a current-stage sign-off blocker
- outer orchestration breadth may expand later only after proof, audit, recovery, and replay discipline have already been established on the narrow signable path
- no future breadth claim may be back-projected into present-stage sign-off language

Current-stage sign-off therefore proves the system by depth before breadth, by closure before convenience, and by governed mutation before orchestration richness.

## 26. Tracer Bullet and Vertical Slice Strategy

This section defines the tracer-bullet doctrine for the **current execution stage**, not the permanent upper bound of the system.

The first serious implementation window must produce one real tracer-bullet vertical slice crossing:

- truth
- validation
- execution
- control
- context
- evidence

The goal is not architectural theatrics.  
The goal is to produce:

- one real governed mutation path
- one real rejection path
- one real replay classification path
- one real failure corpus
- one real recovery basis for future hardening

The current tracer-bullet doctrine is intentionally narrow.

For the current stage and current hardware baseline, the first vertical slice must include:

- a durable truth slice
- one language only
- one patch class only
- one worker profile
- one review path
- one approval path
- one revision seal path
- one evidence capture path

The current-stage signable path is:

Context -> Inference -> PatchProposal -> Validation -> Review -> Approval -> Revision Seal -> Evidence

This path is mandatory because it is the first path that proves:

- context construction is governed
- inference is artifactized rather than trusted raw
- patch intent becomes a governed proposal
- validation is real, not decorative
- review has an admissible artifact form
- approval is serialized and drift-aware
- revision sealing crosses lawful durability boundaries
- evidence closure is preserved for replay, audit, and recovery

The point is not that the system can never support more languages, broader domain surfaces, richer runners, or stronger distributed execution later.  
The point is that the system may not **claim or operationalize** that broader surface before the current stage has produced evidence that the kernel, contracts, and governance model can actually carry it.

Current-stage tracer-bullet rules:

- start narrow
- cross all required governance planes
- produce governed artifacts, not demos
- bind every material action to evidence
- classify replay honestly
- leave reconstructable failure state
- preserve upgrade paths without pretending they already exist
- prefer the narrowest signable path over the broadest impressive path

Current-stage non-blocker rule:

The absence of richer orchestration-shell behavior does not fail the tracer bullet by itself.  
The tracer bullet fails only if the governed kernel path cannot be proven, audited, recovered, or replay-classified honestly.

Success condition:

- one real patch proposal completes the full governed lifecycle
- one invalid mutation path is rejected with evidence
- one replay claim is classified honestly
- one failure path leaves reconstructable evidence
